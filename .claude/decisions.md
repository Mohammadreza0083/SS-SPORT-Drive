## 1a. Engineering practices (owner-required, 2026-10-23)

- **TDD, verified:**
  - Tests are written before every controller, endpoint, handler and domain rule.
  - After implementing, the suite is actually run and must be green before anything is called done or committed.
- **XML documentation** on all .NET code (every method, class, interface and property); TSDoc on exported TypeScript.
- **Specification pattern** for all query and filter logic, used together with the generic repository.
- **Logging:** professional structured logging with **Serilog** (enrichers: correlation ID, environment, user, player). Logs ship to **Grafana Loki** with **Grafana** dashboards and alerts. Secrets, tokens, OTP codes and full emails are never logged.
- **Performance:** benchmark each area of the site (viewer pages, HLS token endpoint, tracking ingest, search, admin APIs) with **k6**. Claude reminds the owner after each area is finished.
- **Git:**
  - One branch per feature or page (`feature/<area>-<name>`).
  - Commit as soon as a feature is implemented and green.
  - Merge to `main` through a PR with passing CI.
- **Always keep `.gitignore` and `.dockerignore` up to date.**
- **API documentation with Scalar:**
  - OpenAPI is generated by ASP.NET Core and rendered with Scalar at `/scalar`.
  - It is clean and complete: summaries, descriptions, tags, schemas, error responses, examples and auth.
  - XML docs flow into it.
  - In production it sits behind admin auth.
- **CI/CD:** a complete, DevOps-friendly pipeline: build, lint, tests, image build, automatic staging deploy, production deploy from tags with approval, migrations as a step, health checks and rollback.

## 2. Architecture (owner-required)

- **CQRS + DDD + Clean Code + SOLID + DRY.**
- **Unit of Work** (wrapping the EF Core `DbContext`).
- A **generic repository** `IRepository<T>` for most aggregates. Specific repositories only when an aggregate needs queries or invariants the generic one can't express. *(This overrides the brief's "no generic repository".)*
- **Specification pattern** encapsulates query criteria, includes, ordering and paging, so the generic repository stays generic.
- **DTO pattern:**
  - Every endpoint takes a request DTO and returns a response DTO, with AutoMapper profiles mapping between them.
  - Domain entities never cross the API boundary.
  - The AutoMapper configuration is validated in tests.
- **Commands** go through repositories and the Unit of Work.
- **Queries read directly:** EF Core `AsNoTracking()` projections to DTOs, with no repository on the read side.
- Stack as in the brief: ASP.NET Core on .NET 10, MediatR, AutoMapper, FluentValidation, Hangfire on PostgreSQL storage, PostgreSQL with EF Core, Cloudflare R2, ffmpeg, a Cloudflare Worker at the edge, and Next.js front-ends (re-confirmed by the owner, 2026-10-23).
- Tests use xUnit, FluentAssertions, NSubstitute, Testcontainers (PostgreSQL) and Playwright.
  - xUnit v3 on Microsoft Testing Platform (required by the .NET 10 SDK).
  - FluentAssertions is pinned to **7.x** (Apache-2.0). Version 8+ needs a paid commercial licence.
  - Front-end and worker unit tests use Vitest.
- **One Next.js app** (`/web`) with route groups for the public site, viewer pages, the admin console and the Telegram Mini App, not separate apps (owner approved, 2026-10-23).
- **Repository layout:** `src/` (Domain, Application, Infrastructure, Api, Workers), `tests/`, `web/`, `edge/`, `deploy/`. Layer boundaries are enforced by architecture tests (NetArchTest).

## 3. Hosting

- **A VPS outside Iran** runs the API, the Telegram bot, the Hangfire workers (ingest, ffmpeg, sync) and PostgreSQL. The provider is still to be chosen. Sizing: about 4 vCPU / 8 GB is enough for the current archive.

## 4. Google Drive & archive

- **Archive size:** about 100 GB so far, so 1–2 transcode workers are enough.
- **Folder structure:** one folder per player, named `SS-SPORT <Full Name>` (e.g. `SS-SPORT Ali Hoshmand`).
  - Inside are subfolders such as `STATS`, `Highlight` and `Full match`. The set varies per player.
  - Ingest and sync must **recurse into subfolders**.
  - **The tag comes from the subfolder name first.** File-name keywords (brief §4) are only the fallback.
  - The player name is suggested from the folder name by stripping the `SS-SPORT ` prefix.
- **No multi-player folders exist.** No split or "Event page" feature is needed.

## 5. Players & positions

- **Positions (6):** `S`, `OH`, `OPP`, `MB`, `L`, **`DS`** (Defensive Specialist, added). Max 2 per player; the first one is primary.
- **Volleybox player ID stays required**, parsed from the URL. No scraping.
- **Waiting list:** any player with incomplete details goes to an admin **waiting list**. "Incomplete" means a missing Volleybox link, photo, position, nationality or name. This covers both archive and analyst folders.
  - Nothing is published and **no link can be created** until an admin fills every field and presses **Publish**.
  - Publish starts transcoding with the watermark and notifies the analyst on Telegram.
  - Players without a Volleybox link are **never** published without one. The team adds them manually.

## 6. Video watermark & media protection

- **Burned into every video at encode time:**
  - SS-SPORT **logo, top-left**.
  - Text **"SS-SPORT · Fetch Your Dreams", bottom-right**.
  - *(Overrides the brief's "top-right ~70 %".)*
  - Changing the watermark later means re-transcoding everything, so finalise its size and position before Phase 1.
  - Test it on real full-match footage, where TV scoreboards often sit in these corners.
- **Dynamic viewer overlay (in the player, not burned in):**
  - The viewer's **email**, small font, **20 % opacity**.
  - It **moves to a new position every few seconds** over the video.
- **No downloads at all:** neither videos nor PDFs.
  - Remove the `AllowDownloads` link setting and every download button.
  - Disable the context menu on the player.
  - The PDF viewer is view-only (pages are rendered, no file is offered).
- **Streaming:** HLS segments only. Originals are never exposed.
- **Signed tokens:**
  - HLS URLs are HMAC-signed and **expire after 30 minutes**.
  - While the viewer is actively watching, the player **refreshes the token in the background**, extending it another 30 minutes.
- **No paid DRM** (Widevine/FairPlay rejected for cost and complexity). Screen recording can't be fully blocked on the web; the email overlay is the deterrent.

## 7. Viewer access

- **Forwarding:** anyone may open a forwarded personal link after verifying their email with an OTP code. Every forward is logged, and admins are alerted with Keep / Block actions.
- **No `/p/{slug}` public showcase pages.** Only personal `/r/{code}` links show content.
- **Public home page** (`drive.ss-sport.co`):
  - Visitors search players by name, with a position filter.
  - A result shows the full player page (photo, name, position, flag, counts), but **videos, stats and PDFs are blurred and locked**. The backend must not send real media or document URLs for locked pages.
  - **Request access** form: email + description ("club or agency, role, what you're looking for").
  - **Anti-spam:**
    - The email must be OTP-verified before the request is created.
    - Cloudflare Turnstile protects the form.
    - Rate limits apply per IP, per email and per player.
  - The request goes to admins (console + bot).
  - **When an admin approves it, a normal personal `/r/` link is created automatically and emailed to the requester.**

## 7a. Accounts & login (owner decision, 2026-10-23)

- **Admin console login:**
  - Email **magic link**: the admin enters their email and receives a one-time sign-in link.
  - The session lasts **7 days**, then the admin must sign in again.
  - *(Replaces the brief's Telegram Login for the console. The bot still identifies users by Telegram ID.)*
- **Viewer accounts:**
  - Viewers (clubs, scouts, agents) can sign in with an email magic link from a login page.
  - The session lasts **1 day**.
  - Signing in only serves to skip the email/OTP step when requesting access (confirmed by the owner after the CEO dropped the dashboard).
- **No viewer (user) dashboard (CEO decision):**
  - Viewers get no dashboard.
  - They reach players only through the personal links emailed to them.
  - After signing in they return to the public search.
  - *(This overrides the earlier viewer-dashboard decision. Backlog P-6 / Jira SSD-97 is dropped.)*
- **Home page:**
  - Has a **Sign in** button.
  - When signed in, it shows the viewer's email and a Sign out button.
  - A signed-in viewer requests access in one click, without retyping an email or OTP.
- **Admin visibility:**
  - Everything is logged per viewer: which players and videos they watched, how many times, minutes watched, last seen and access expiry.
  - Admins see it in the console (Viewers page + viewer profile).
- **Access requests:** a dedicated admin page (also announced by the bot) where admins review each request and approve, approve with changes (expiry, players) or decline. Approval auto-creates the personal link and emails it.

## 8. Email

- **OTP codes:** **Resend is primary**, **Brevo is the fallback**.
- **All other email** (link invites, approval emails, nudges) goes through **Google SMTP**.
- **Every email send goes through a Hangfire queue**, OTP included:
  - It retries automatically on failure.
  - It fails over Resend → Brevo for OTP.
  - The queue is always visible to admins (an "Email queue" page in the console).
- **Contact address** shown to viewers: `info@ss-sport.co`.
