## 1b. Security baseline (owner, 2026-11-01)

Standing rules for every feature. Each control gets tests, and nothing is committed that breaks one.

1. **No secrets in code.** Keys, tokens, passwords and connection strings come only from environment variables or secret stores (the git-ignored `.env` locally; `.env.example` holds placeholders only). They never appear in commits, logs, Docker images, front-end bundles or realistic-looking test fixtures.
2. **Database locked down.** PostgreSQL is never publicly reachable (bound to `127.0.0.1` locally, private Docker network on the VPS). The app connects with a least-privilege role (no superuser; migrations use a separate role). TLS in production. Backups are encrypted.
3. **Server-side validation of every input,** through FluentValidation in the MediatR pipeline. Client-side checks are only for UX.
4. **XSS is always blocked.** Output is encoded, user data is never rendered as raw HTML, and a Content-Security-Policy applies. `dangerouslySetInnerHTML` is allowed only for static, code-built scripts (never user data).
   - **Web CSP is static, with `'unsafe-inline'` scripts (owner, 2026-11-01).** A per-request nonce would force every page to render dynamically and switch off `cacheComponents`/Partial Prerendering; the owner chose to keep caching. Everything else is locked to our own origins (`'self'`, `https://*.ss-sport.co` for media). The site may not be framed; the Mini App may be framed only by `https://web.telegram.org` and loads `https://telegram.org`'s script. Built in `web/src/lib/security-headers.ts`.
   - **The API's CSP** is `default-src 'none'` (JSON only); the Scalar page, never served in production, has none.
5. **Admin area locked.** Admin pages and every admin API require an authenticated session with the Admin role, checked on the server (deny by default). Scalar sits behind admin auth in production.
6. **HTTPS forced.** HTTPS redirection and HSTS in production; cookies are Secure-only.
7. **Hash with salt.** Passwords (if ever introduced) use a slow salted hash (Argon2id or the ASP.NET Core `PasswordHasher`). OTP codes are stored hashed with a per-code salt. Magic-link and session tokens are stored only as HMAC-SHA256 hashes with a server-side pepper. Raw secrets are never stored, and comparisons are constant-time.
8. **Suspicious activity is logged:** failed sign-ins and OTPs, wrong webhook secrets, rate-limit rejections, CSRF failures, forbidden admin calls. They are structured Serilog warnings (no secrets, tokens or full emails) with Grafana/Loki alerts.
9. **Parameterized queries only.** EF Core LINQ or interpolated `FromSql`; SQL is never built by string concatenation.
10. **Rate limiting** (ASP.NET Core rate limiter, partitioned by IP and identity) on sign-in, OTP, magic-link, access-request, webhook and other public endpoints. Rejections return 429 with `Retry-After`.
11. **CORS** allows only the explicit origin list (`Cors__AllowedOrigins`); never a wildcard with credentials.
12. **Security headers** on the API and the Next.js app: CSP, HSTS, `X-Content-Type-Options: nosniff`, `frame-ancestors`/`X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`.
13. **Session cookies are secure:** `HttpOnly`, `Secure`, `SameSite=Lax` (or `Strict`), `__Host-` prefix, lifetimes per §7a (admin 7 days, viewer 1 day).
14. **CSRF protection** (anti-forgery tokens) on every cookie-authenticated state-changing request. Header-authenticated calls (Mini App initData, Telegram webhook secret) are exempt.

**How the first pass is built (O-9 / SSD-123, 2026-11-01):**
- **API (`src/SsSport.Drive.Api/Security`):**
  - Forwarded headers are honoured only from `Security__TrustedProxies` (addresses or CIDR; loopback always).
  - Outside development, HTTP is redirected with 308 to HTTPS on port 443 (`/health` exempt, for container probes). HTTPS answers carry `max-age=31536000; includeSubDomains`; preload is not requested yet.
  - Headers are written as the response starts, so errors and 429s carry them too. The `Server` header is off.
  - Rate limits: a fixed one-minute window per client address, `RateLimiting__PermitsPerMinute` (300). The webhook has its own `RateLimiting__WebhookPermitsPerMinute` (1800). Health probes are never limited. Refusals are 429 ProblemDetails with `Retry-After`, logged as warnings, and documented on every operation in Scalar. OTP and magic-link endpoints add tighter policies when they are built.
- **Web (`web/src/lib/security-headers.ts`):** headers come from `next.config.ts`, with HSTS in production builds and no `X-Powered-By`.
- **Database role:**
  - `migrate` connects as the owner and creates or updates the app role named by `Database__AppUser` / `Database__AppPassword` (compose: `DB_APP_USER` / `DB_APP_PASSWORD`). Running it again rotates the password.
  - The role can log in and run SELECT/INSERT/UPDATE/DELETE on the tables of `public` and `hangfire`, and use their sequences. Default privileges cover tables later migrations create. It has no DDL, TRUNCATE, role or database powers.
  - The password is sent only as a SCRAM-SHA-256 verifier with a random salt, built in .NET. The DDL is assembled by PostgreSQL's `format()` from bind parameters.
  - Bad settings (an invalid name, a `pg_` prefix, the owner's own name, a password under 16 printable ASCII characters) stop `migrate` before anything changes.
  - The API and workers in Docker connect as the role. A local `dotnet run` still uses the owner. The production compose (O-1) gives each container only its own secrets.

## 2. Architecture (owner-required)

- **CQRS + DDD + Clean Code + SOLID + DRY.**
- **Unit of Work** (wrapping the EF Core `DbContext`).
- A **generic repository** `IRepository<T>` for most aggregates. Specific repositories only when an aggregate needs queries or invariants the generic one can't express. *(This overrides the brief's "no generic repository".)*
- **Specification pattern** encapsulates query criteria, includes, ordering and paging, so the generic repository stays generic.
- **DTO pattern:**
  - Every endpoint takes a request DTO and returns a response DTO.
  - **Mapping uses Mapperly** (`Riok.Mapperly`, Apache-2.0), a compile-time source generator. It replaced AutoMapper on 2026-10-25 (owner; see D-9 below).
  - Domain entities never cross the API boundary. Architecture tests enforce it: `*Dto` types reference no Domain type, and the API references no Domain model namespace (only `DomainException`).
- **DTOs (D-9, owner-approved 2026-10-25):**
  - **Response DTOs** exist for players (summary + details), assets + renditions, Drive folders, users and audit entries. Each has one `[Mapper]` static class next to it (`player.ToDetailsDto()`, `asset.ToDto()`…).
  - **Request DTOs** come with each endpoint.
  - **Values are flattened:**
    - name, slug and photo key as text;
    - nationality as `NationalityCode` + `NationalityName`;
    - positions as codes, primary first;
    - Volleybox as `VolleyboxId` + `VolleyboxUrl`;
    - tags as names;
    - rendition quality as its height;
    - enums as their names.
  - API JSON also writes any enum by name (`JsonStringEnumConverter`).
  - `UserDto` carries the **full email**: it is admin-only, and emails are masked only in logs.
  - **Mappers are strict:** a DTO member without a mapping is a **build error** (Mapperly `RMG012`), so there is no runtime "configuration valid" test.
  - **Read side:** queries load with `AsNoTracking()` and map with these mappers. Value objects stored through converters cannot be projected member-by-member in SQL.
- **Why not AutoMapper:**
  - AutoMapper 14.0.0, the last MIT version, has a **high-severity DoS advisory (GHSA-rvv3-g6hj-g44x)**: unbounded recursion on deeply nested graphs.
  - Only the commercial 15.1.1+/16.1.1 fix it.
  - The re-enabled NuGet audit fails the build on it.
  - The owner chose Mapperly (2026-10-25).
- **Commands** go through repositories and the Unit of Work.
- **Queries read directly:** EF Core `AsNoTracking()` projections to DTOs, with no repository on the read side.
- **Domain building blocks (D-1, 2026-10-24):** they live in `SsSport.Drive.Domain.Primitives`.
  - `Entity<TId>`: equal when the type and `Id` match.
  - `AggregateRoot<TId>`: collects `IDomainEvent`s until they are dispatched after saving. Events are plain records; the Domain layer has no MediatR dependency.
  - **Value objects are C# `record`s.** There is no `ValueObject` base class, because records already give value equality (brief: DDD without over-engineering).
  - **A broken domain rule throws `DomainException`** with a stable code such as `player.too_many_positions`. The API maps that code to a ProblemDetails response; there is no Result type in the domain.
- **Persistence ports (D-2, 2026-10-24):**
  - `IRepository<TAggregate, TId>` and `IUnitOfWork` live in `Application/Abstractions/Persistence`. The EF Core implementations live in `Infrastructure/Persistence`.
  - **Repositories only stage changes** (`GetByIdAsync`, `Add`, `Remove`). Edits to a loaded aggregate are tracked, so there is no `Update`. Only `IUnitOfWork.SaveChangesAsync` writes, as one transaction.
  - **Specifications (D-2b, 2026-10-24):** they use the **Ardalis.Specification** library itself (MIT), not a home-grown copy.
    - The Application layer depends only on the core package (no EF Core). Infrastructure evaluates specifications with `Ardalis.Specification.EntityFrameworkCore`.
    - The repository offers `FirstOrDefaultAsync`, `ListAsync`, `CountAsync` and `AnyAsync` taking a specification. Count and Any apply only the criteria and ignore paging.
    - Aggregates loaded this way are tracked, like `GetByIdAsync`.
- **API docs & errors (D-2c, 2026-10-24):**
  - The OpenAPI document is served at `/openapi/v1.json` (`Microsoft.AspNetCore.OpenApi`) and rendered by **Scalar** at `/scalar`.
  - Both are mapped in **every environment except Production**. In production they stay off until admin sign-in exists (A-1); then they go behind admin auth.
  - Local `dotnet run` gets `ASPNETCORE_ENVIRONMENT=Development` from `.env`.
  - **Every endpoint** carries a name (operationId), a summary, a description, a tag and all its responses. Minimal-API handlers are named methods, not inline lambdas, so XML docs apply.
  - **Errors are RFC 9457 ProblemDetails** (`AddProblemDetails` + `UseExceptionHandler`).
    - A `DomainException` becomes **422** with its stable `code` extension; the exception message is never sent.
    - Any other exception becomes a generic **500**.
    - Validation errors become 400 (D-3).
  - **Auth schemes are added to the document with the auth features themselves** (admin magic-link session A-1, viewer session, Telegram webhook secret T-1). Nothing is authenticated yet, so none are documented today.
- **MediatR pipeline (D-3, 2026-10-24):**
  - **Contracts:** `ICommand` / `ICommand<T>` change state; `IQuery<T>` only reads. There are matching handler interfaces.
  - **Behaviour order:** logging → authorization → validation → transaction → handler. Authorization runs before validation, so anonymous callers learn nothing about a request's rules.
  - **Logging:** request type name and duration only, as structured properties. **Request data is never logged** (emails, OTP codes).
  - **Authorization:** a request that implements `IAuthorizedRequest` needs a signed-in caller (otherwise 401) with one of its `RequiredRoles` (otherwise 403). The caller comes from `ICurrentUser`.
    - The API reads it from the request's principal. Hosts without users see an anonymous caller.
    - Real sign-in arrives with A-1 and the viewer sign-in.
  - **Validation:** FluentValidation validators run before the handler. Failures become 400 ValidationProblemDetails, with errors per field.
  - **Transaction:** commands are committed by the unit of work after a successful handler. Handlers never call `SaveChangesAsync`, and queries never write.
  - **Domain events:** after a successful save, the unit of work dispatches the events of every tracked aggregate (in raise order) to `IDomainEventHandler<TEvent>`s and clears them. A failed save dispatches nothing. MediatR is not used for domain events, so the Domain layer stays framework-free.
  - **There is one `AppDbContext` per request scope**, shared by the repositories and the unit of work. It uses the shared `NpgsqlDataSource`.
  - Entity mappings are `IEntityTypeConfiguration` classes, picked up automatically (D-8).
  - Domain events are never mapped as data. They are dispatched after saving once the MediatR pipeline exists (D-3).
- Stack as in the brief: ASP.NET Core on .NET 10, MediatR, Mapperly (replaced AutoMapper, 2026-10-25), FluentValidation, Hangfire on PostgreSQL storage, PostgreSQL with EF Core, Cloudflare R2, ffmpeg, a Cloudflare Worker at the edge, and Next.js front-ends (re-confirmed by the owner, 2026-10-23).
- Tests use xUnit, FluentAssertions, NSubstitute, Testcontainers (PostgreSQL) and Playwright.
  - xUnit v3 on Microsoft Testing Platform (required by the .NET 10 SDK).
  - FluentAssertions is pinned to **7.x** (Apache-2.0). Version 8+ needs a paid commercial licence.
- **MediatR is pinned to its last free version (owner, 2026-10-24):**
  - **MediatR 12.5.0** (Apache-2.0). MediatR 13+ is commercial: a Community licence needs registration and a key.
  - Never upgrade it past this version without asking.
  - AutoMapper was pinned to 14.0.0 the same way and has since been **replaced by Mapperly** (see DTO pattern above).
  - FluentValidation stays on the latest version (Apache-2.0).
  - Front-end and worker unit tests use Vitest.
- **One Next.js app** (`/web`) with route groups for the public site, viewer pages, the admin console and the Telegram Mini App, not separate apps (owner approved, 2026-10-23).
- **Repository layout:** `src/` (Domain, Application, Infrastructure, Api, Workers), `tests/`, `web/`, `edge/`, `deploy/`. Layer boundaries are enforced by architecture tests (NetArchTest).

## 2b. Pagination (owner, 2026-10-25)

- **Never send every entity at once.** No endpoint, Mini App screen or bot message returns an unbounded list. Every list that can grow is paged on the server.
- **Where it applies:** players (console list, waiting list, analyst's "my players"), public search results, assets in the console, users, the audit log, viewers and recipients, share links, access requests, tracking events and sessions, live activity, sync jobs and the email queue. Any new list is paged by default.
- **Exempt:** small fixed catalogues that are sent whole and cached (countries, positions, roles), and CSV exports, which stream instead of paging.
- **Paging happens in the database:** `Skip`/`Take` run in SQL. A list is never loaded whole and paged in memory. The total count uses the same criteria without paging.
- **Stable order:** every paged query has an explicit order with a unique tie-breaker (the id), so items never repeat or vanish between pages.
- **Two styles:**
  - **Offset paging** (`page`, `pageSize`) for admin tables and search, where the total and page numbers are shown.
  - **Cursor (keyset) paging** (`cursor`, `pageSize`) for large, append-only feeds: audit log, tracking events, live activity, infinite scroll.
- **Limits:** `pageSize` defaults to **20** and is at most **100**. A larger or invalid value is a 400 validation error.
- **One response shape:** `PagedResult<T>` with `items`, `page`, `pageSize`, `totalCount`, `totalPages`; cursor lists return `items` + `nextCursor` (`null` on the last page). The shapes are documented in Scalar.
- **Front-end:** tables show page controls, and page and size live in the URL (with the filters, A-3). The bot and Mini App page lists with Next/Previous buttons.
- Built once as shared building blocks (D-11 / SSD-106) and used by every list endpoint after that.
- **How it is built (D-11, owner-approved 2026-10-25, done 2026-10-29):**
  - **Queries:** a list query implements `IPagedQuery<TItem>` (with `PageRequest Paging`) or `ICursorQuery<TItem>` (with `CursorRequest Paging`). Shared open-generic validators check the paging of every such query, so a query writes no paging rules. Errors are keyed `page`, `pageSize` and `cursor`, the names the client sent.
  - **Reading:** handlers call `IPagedReader`. It takes a specification for criteria, includes and (for offset lists) the order. **Paging comes from the request, never from the specification:** a specification that pages itself is refused. An offset specification without an order is refused too. The reader appends the id as the last order key, reads untracked and maps each row with the DTO mapper.
  - **Cursors:** the reader orders by one key and then the id, and filters with a PostgreSQL row comparison (`(key, id) < (@key, @id)`), so deep pages stay fast. It reads one extra row to know whether a next page exists. The cursor is base64url JSON holding the key's type, the key and the id. It is not signed, because it only moves within a list the caller may already read. A cursor from a list with another key type is a 400.
  - **API:** endpoints bind `[AsParameters] PageParameters` / `CursorParameters`, and `.WithPagedResponse<T>()` / `.WithCursorResponse<T>()` document the 200 page (with an example) and the 400 in Scalar.
  - **Guard:** an architecture test fails any Application query whose result is a bare collection unless it carries `[UnpagedList("reason")]`, the exemption for fixed catalogues.

## 3a. Configuration & secrets (owner, 2026-10-23)

- **One git-ignored `.env` at the repository root** holds every setting and secret. `.env.example` is the committed template.
  - Docker Compose reads it (`env_file`).
  - The API and workers load it with **DotNetEnv** for local `dotnet run`. Real environment variables always win.
  - The web app loads it in `next.config.ts`.
- **Telegram webhook (T-1, owner-approved 2026-10-25):**
  - **`POST /telegram/webhook`** accepts only calls whose `X-Telegram-Bot-Api-Secret-Token` header matches `Telegram__WebhookSecret`.
    - The comparison is constant-time, on SHA-256 hashes, so neither the value nor the length leaks.
    - **An empty secret disables the webhook:** every call gets 401 (fail closed). The local stack and CI run without Telegram settings, and a set secret is format-checked at start-up.
  - **Authenticated updates are always answered 200,** even when processing fails (the error is logged). A non-2xx would make Telegram re-deliver in a loop. A body that is not an update gets 400.
  - **Re-deliveries are skipped:** each `update_id` is recorded in **`telegram_updates`** with `INSERT … ON CONFLICT DO NOTHING`, which is safe under concurrency. Old rows get a clean-up job later.
  - **The update becomes `HandleTelegramUpdateCommand`** (update id, kind, sender id) through MediatR. **Message text is never put in the command or the logs.** Routing to features starts with T-2.
  - **`Telegram.Bot` 22.10.3.3** (MIT) stays in Infrastructure and the API; an architecture test keeps it out of the Application layer.
  - **Registration is a separate step:** `dotnet SsSport.Drive.Api.dll telegram-set-webhook` calls `setWebhook` (HTTPS URL, secret, updates `message`, `callback_query`, `my_chat_member`; pending updates kept) and exits. It never runs on start-up. There is no IP allow-list; the secret is enough.
  - **Local development has no webhook:** there is no public URL, and Telegram is blocked in Iran without a VPN. Tests use synthetic updates.
  - **Proxy (owner, 2026-10-25):** the owner's VPN (v2rayN) exposes a mixed HTTP/SOCKS proxy at **`127.0.0.1:10808`**. `Telegram__Proxy` (e.g. `http://127.0.0.1:10808`, or `http://host.docker.internal:10808` inside Docker) routes Bot API calls through it. It stays empty on the VPS.
  - The webhook is documented in Scalar under the "Telegram" tag, with an `apiKey`-in-header security scheme (`TelegramWebhookSecret`), an example update and its 200/400/401 responses.
- **Bot access flow (T-2, owner-approved 2026-10-25):**

- **Mini App auth (T-3, owner-approved 2026-10-29):**
  - **Per request, nothing stored:** the Mini App sends `Telegram.WebApp.initData` as `Authorization: tma <initData>` with every call. The API's `TelegramMiniApp` scheme recomputes Telegram's HMAC-SHA256 signature under our bot token (`HMAC-SHA256("WebAppData", botToken)`), compares in constant time, and needs `auth_date` at most **24 hours** old (5 minutes of clock skew allowed).
  - **401 vs 403:** missing, forged, tampered or stale initData → 401. A correctly signed Telegram user who is not an active team member (unknown, Pending, Declined, Removed) → 403. Only an active user gets the user-id and role claims, so the existing MediatR role checks do the rest.
  - **`GET /miniapp/me`** returns the caller's profile (id, Telegram id, display name, username, role) read from our database, never from initData, and never the email.
  - **The browser never calls the API across origins:** the web app's `/api/miniapp/me` route forwards only the Authorization header to `API_BASE_URL`.
  - **Menu button:** `telegram-set-webhook` sets "Open Drive" to `Telegram__MiniAppUrl` (HTTPS only). Locally it stays unset, because Telegram cannot open a local URL.
  - initData and its hash are never logged, only the rejection reason and the Telegram id.

- **Bot notices leave the request (T-6c, owner-approved 2026-10-31; found by the K-9 benchmark):**
  - **Why:** every saved player change waited for Telegram inside the request (about 1 s per round trip), so a details edit took 929 ms at p95 against 300 ms.
  - **Every bot notice** goes through a background job: the progress message (T-6a), the "folder added by someone else" notice (T-5), and the access request, approval and decline messages (T-2). The request saves, enqueues and answers. Bot replies to the user's own button or command stay inline, because the user is waiting for them.
  - **Hangfire on PostgreSQL** (the stack decided in §1), owner's choice over an in-memory queue, so a queued notice survives a restart.
  - **The Hangfire server runs inside the API** (owner's choice) and serves only the notice queue. The heavy jobs (ingest, ffmpeg, sync) go to the workers process in Epic 3 and share the same Hangfire storage.
  - **How it is built:**
    - A notice is an `IBackgroundEventHandler<TEvent>` (Application). After the save, the dispatcher still runs inline `IDomainEventHandler`s, and it queues an event that has background handlers through the `IBackgroundEventQueue` port, with the caller as the actor (`EventContext`), because a job has no signed-in user.
    - Infrastructure stores it as a Hangfire job (`BotNoticeJob`) on the `notices` queue: the event's type name, its JSON and the actor id. Only types from the Domain assembly that are domain events are read back.
    - **One worker** serves the queue, so a player's notices run in the order they were raised. The queue is polled every second, and a failed job is retried 3 times. Telegram failures are still caught and logged as before (T-6a), so they are not retried.
    - **Schema:** Hangfire's tables live in their own `hangfire` schema. `migrate` installs and upgrades them, and start-up never does (§2).
    - Without a database, the API still starts and the Hangfire server stays off.
    - If the queue itself cannot be reached, the change stays saved and a Warning is logged.
    - **No shared Hangfire state:** the storage and the job activator are registered per DI container, not taken from Hangfire's process-wide `JobStorage.Current` / `JobActivator.Current`. With those statics, several hosts in one process (the test suite) took each other's jobs.
    - **Packages:** Hangfire.Core / Hangfire.NetCore 1.8.25 and Hangfire.PostgreSql 1.21.1, all LGPL-3.0. They are used unmodified as packages, which is compatible with the proprietary licence.
    - **Dashboard:** there is none for now. It comes behind admin auth with the admin console (Epic 7).
- **Notification rules (T-8, owner-approved 2026-11-12, all four of Claude's proposals accepted):**
  - **What the rules cover:** the notices that ping a team member about something someone else did: "folder added by someone else" (T-5) and the new **"player published"** notice to the owning analyst (§5, on `PlayerPublished`). Later notices (sync, build done, admin alerts from I-6, T-6b and L-7) use the same path.

    - Replies to the user's own button or command.
    - Access request, approval and decline messages. They stay **immediate** because someone is waiting for the answer (owner's choice).
  - **Throttle per recipient:** at most one notice message per team member every **10 minutes**, counted per recipient, not per player (owner's choice).
  - **Quiet hours 23:00–08:00 Tehran:** notices are **held and sent at 08:00** as one message, not sent silently (owner's choice). Start included, end excluded. A throttled notice whose turn falls in the quiet hours also waits for 08:00.
  - **Grouping:** everything held for a recipient goes out together. One notice is sent as written. Several get a header with their count ("🔔 3 updates while notices were paused:"), grouped by player in the order the players first came up. They are checked at start-up. The same start and end turns quiet hours off. Editing them in the console comes with A-10; per-user preferences are not planned.
  - **How it is built:**
    - The Domain has `NotificationRules`, which works out the next send time from now and the last message. It also has a `NoticeBox` aggregate, one per team member (`notice_boxes`), whose held lines live in `pending_notices`. A box knows its `DueAt` and `LastSentAt`.
    - A notice handler hands its line to `IBotNoticeOutbox`. The first notice in a quiet period is sent at once, inside the notice job. Later ones are held.
    - `SendDueNoticesCommand` (MediatR) sends every due box. It pages through the due boxes in SQL (50 per page, oldest due first) and saves after each box, so a crash never sends one twice. It is run by the recurring Hangfire job `bot-notices-due`, every minute, on the `notices` queue with its single worker, so it never overlaps a notice job.
    - **`migrate` registers the recurring job**, right after installing Hangfire's schema. The API never registers it on start-up, so instances never race and a host started before `migrate` cannot fail on it.
    - **Telegram down:** the notices stay held and are tried again one throttle later (Warning logged).
    - **Recipient left the team:** their held notices are dropped (Information logged).
  - **Time zone:** Linux images use the system tz database. A Windows host with invariant globalization cannot map `Asia/Tehran`, so it falls back to a fixed UTC+3:30, which is correct because Iran has had no daylight saving time since 2022.
  - **Tests:** the API test process turns quiet hours off (`Notifications__QuietHours*` = `00:00`), so tests that expect an immediate notice pass at any hour. `BotNoticeRulesTests` sets the owner's rules back and drives its own clock.
- **SQL logging (D-14, owner-approved 2026-11-01; found by the K-9 benchmark):**
  - **Why:** the base config logged the text of every SQL command at Information, in every environment (about 92 000 commands, 90 MB, in one load run). Parameter values were never logged.
  - **EF Core logs at Warning** in the base `appsettings.json` of the API and the workers, so in every environment, Development included. Failed commands are still logged as Errors.
  - **Turning SQL back on** for a while: `Logging__LogLevel__Microsoft.EntityFrameworkCore.Database.Command=Information`.
  - **Slow queries are logged:** a command that takes at least `Database__SlowQueryThresholdMs` (default **500 ms**) is a Warning, with its duration and its SQL text, never its parameter values.
  - The k6 run measures what SQL logging cost, in Production mode.

- **Database connection pools (D-15, owner-approved 2026-11-06; found during D-14):**
  - **Why:** every process could open Npgsql's default of 100 connections, which is also PostgreSQL's whole `max_connections`. Under load PostgreSQL refused new ones ("too many clients already") and requests failed with 500.
  - **One capped pool per process:** `Database__MaxPoolSize` sets it, and it wins over any pool size in the connection string. The **API has 40** (its Hangfire server shares them), the **workers 20**, each set in its own base `appsettings.json`. That leaves 40 of PostgreSQL's 100 for `migrate`, a `psql` session and the reserved superuser slots. A test keeps API + workers at 80 or less. It is never set in the shared `.env`, because both hosts read it. Allowed range: 1-90; the default is 20.
  - **Fail fast:** opening a connection, including the wait for a free pooled one, takes at most `Database__PoolTimeoutSeconds` (default **5 s**, range 1-60).
  - **Busy database is a 503:** a full pool or a full server is answered with **503**, `code: database.busy` and `Retry-After: 1`, logged as a **Warning** without SQL or connection details.
  - **No PgBouncer and no higher `max_connections` for now.** They come back if the API ever runs as several instances.
- **Concurrent edits and log levels (D-13, owner-approved 2026-10-29; found by the K-8 benchmark):**
  - **Concurrent saves:** when two requests save the same aggregate at once, PostgreSQL's `xmin` check still refuses the later save, so nothing is overwritten. The unit of work now reports that as `ConcurrencyConflictException`, and the API answers **409** with `code: concurrency.conflict` (it used to be a raw 500). The Mini App tells the analyst to try again.
  - **Log levels** (`LoggingBehavior`): refusals the API answers on purpose (401, 403, 400, 404, 409, 422) are logged at **Information**, with the reason as a structured `Reason` property (the rule code or the refusal type) and no stack trace. An outside service being down (503) is a **Warning**. Only real failures are **Error**, so Grafana error alerts mean something.

## 4b. Folders, assets & renditions (D-6, owner-approved 2026-10-24)

- **`DriveFolder` is its own aggregate.**
  - It records the player, the Drive folder id, its name, when it was linked and when it last synced.
  - Its access is `Ok` or `Lost`. Losing access raises `FolderAccessLost` once; the next successful sync raises `FolderAccessRestored`.
  - A player can have several folders.
- **`Asset` is its own aggregate, one per file.**
  - **Kind** comes from the extension:
    - `Video`: mp4, mov, m4v.
    - `Document`: pdf, png, jpg/jpeg. Stats screenshots are documents.
    - `Scout`: dvw.
  
    Other files and zero-byte files are rejected (`asset.unsupported_file_type`, `asset.file_empty`).
  - **Source** is `Drive` or `Archive` (the rclone backup).
  - **Visibility** is `Visible` or `Hidden`.
  - **Processing:** `Queued → Copying → Processing → Ready`, or `Failed` with a reason. An original already in the backup skips `Copying`. `Retry` re-queues a failed asset from the start.
  - **Sync rules:**
    - **Renamed in Drive:** the title follows the new name, unless someone edited it by hand (`TitleIsCustom`).
    - **Replaced** (same file, new md5): the version goes up, processed output is dropped and the asset is queued again. The same md5 changes nothing, and the kind cannot change.
    - **Removed from Drive:** the asset is hidden and `RemovedFromSourceAt` is recorded. Nothing is deleted, and `Show()` restores it.
  - **Events:** `AssetAdded`, `AssetReady`, `AssetFailed`, `AssetHidden`, `AssetReplaced`.
- **`Rendition`s belong to their asset.**
  - Qualities are 360/720/1080, **never above the source height**. 360p is always made.
  - A video is ready only when every planned rendition is ready.
- **`AssetTagger`:**
  - The subfolder name wins. It covers every archive spelling of full match, highlights and STATS, and nested match or competition folders keep the tag.
  - The fallback is file-name keywords on whole words or word starts:
    - `hl`/`highlight*` → Highlight
    - `spike*`/`attack*` → Spike
    - `serve*` → Serve
    - `block*` → Block
    - `recep*`/`receiv*`/`pass*` → Reception
    - `def`/`defen*`/`dig(s)` → Defence
    - `full*`/`match*`/`game*` → FullMatch
  - Tags are flags, so several can apply. **`Stats`** is a new tag.
  - **Title:** the match folder below a tag folder if there is one, otherwise the file name without its extension.
- **Hero:**
  - `Player.HeroAssetId` holds the choice. `SetHero` and `ClearHero` set it by hand.
  - The automatic pick (shortest highlight) belongs in the Application layer.
- **`StorageKey`** is a shared value object for object keys. It is relative, with no traversal, URL or backslash, and allows spaces because backup paths mirror Drive names.

Pasting the URL into VLC, another browser or another viewer's browser gives 403, with no reason given.

    - Playlists are `Cache-Control: private, no-store`; segments `private, max-age=1800`.
    - The player renews the token every 20 minutes while playing, and on play after a longer pause. With hls.js the token is swapped into each following request (no interruption); with native HLS (iPhone/iPad) the source is swapped and playback resumes at the same second.
    - V-5b adds the API endpoint that issues tokens on the viewer session, wires the player to it, and routes short links on the edge.

## 7. Viewer access

- **Forwarding:** anyone may open a forwarded personal link after verifying their email with an OTP code. Every forward is logged, and admins are alerted with Keep / Block actions.
- **No `/p/{slug}` public showcase pages.** Only personal `/r/{code}` links show content.
- **Personal share links (L-1, built 2026-11-01; the owner approved starting L-1, the choices below are to be confirmed):**
  - **Model (brief §5):**
    - A `Recipient` has a name, an optional organisation and country, and one to five emails.
    - A `ShareLink` holds:
      - a six-character code;
      - its type: `Personal` for one player, `Roster` for up to 20, in page order;
      - an optional note (up to 500 characters);
      - an expiry of 7, 30 or 90 days, or never;
      - a status: `Active`, `Paused` or `Revoked`;
      - the switches `VerifyOnNewDevice` (default on), `AllowForwarding` (default on), `ForwardingScope` (`AnyEmail` default, or `SameDomain`) and `NotifyOnOpen` (default off).
    - There is no `AllowDownloads` (decisions §6).
    - Choosing single files instead of "all visible" waits for the New share link modal (A-6).
  - **Code:** six random characters from a 56-letter alphabet without look-alikes (no 0/O, 1/l/I), drawn with a cryptographic generator. Codes are unique (database index) and case-sensitive.
  - **Rules:**
    - Links only for published players.
    - Pause and resume can be undone; revoke is final. A revoked link cannot be resumed or re-dated.
    - A new expiry re-opens an expired link.
    - Created, paused, resumed, expiry changed and revoked are audited under the `share_link.*` actions.
  - **Who:** admins only. Until the admin console session (A-1) exists, admins call `/admin/links` with the Mini App's signed initData; the console session joins the same endpoints later.
  - **Public check:** `GET /links/{code}` answers type, player count and a masked hint of the recipient's first email (`m***@lube.it`) for the L-2 email gate, and nothing about the players.
  - **No probing:** unknown, malformed, paused, revoked and expired codes all answer the same 404 `share_link.unavailable`. Per-IP rate limits on this endpoint come with L-2's code-sending limits.
  - **The `/r/{code}` web page** (email gate, then the player page; the "link has expired" page for links that do not open) is built with L-2 from the canvas `Gate` artboard.
- **Email gate, OTP and device binding (L-2; owner approved the plan 2026-11-06):**
  - **Gate card:** before the gate, `GET /links/{code}` also answers the player's name, primary position and nationality for a Personal link (the canvas `Gate` card), and only the count for a Roster. No photo, videos or files before the gate. These are the same facts the public home page shows.
  - **Which emails pass:**
    - One of the recipient's emails always passes.
    - Another email passes as a **forward** when the link allows forwarding and the scope fits (`SameDomain` = the domain of one of the recipient's emails).
    - Anything else is refused with 422 `share_link.email_not_allowed`.
    - L-3 adds the forward alert and Keep / Block.
  - **Codes:**
    - 6 digits, valid **10 minutes**, **5 tries**; the 5th wrong try spends the code (`email_code.exhausted`).
    - A new code may be asked for after **60 seconds**, at most **5 codes per email per link per hour** (429 `email_code.too_many`, with `Retry-After`).
    - The code is drawn **inside the background job that sends it**, so it never sits in the request, the Hangfire job arguments or a log. Only `HMAC-SHA256(pepper, salt + code)` with a per-code random salt is stored, and it is compared in constant time.
    - The pepper and token key is `Viewer__TokenKey` (base64, 32 bytes or more).
  - **Sending:**
    - The code is sent by a Hangfire job: Resend first, Brevo when Resend fails.
    - Until L-4 builds the email queue (own queue, admin page, Google SMTP), the job runs on the bot-notices queue.
    - In development without provider keys, `Email__PickupDirectory` writes the mail as an `.eml` file instead. Production refuses the pickup directory.
  - **Device and session:**
    - **Device:** the browser gets `__Host-ssd_dev`, remembered **90 days** (canvas). It is trusted per link: one row per device and link (`trusted_devices`), with the verified email and whether it was a forward.
    - **Session:** `__Host-ssd_vs` lasts **1 day** (§7a) and belongs to one link and one email. When it runs out, a trusted device gets a new session silently, with no new code.
    - **Edge cookie:** the edge Worker's cookie is renamed from `ssd_vs` to `__Host-ssd_vs` to meet the cookie rule in §1b.
    - **Storage and cookie flags:** tokens are stored only as HMAC-SHA256 hashes. Cookies are `HttpOnly`, `Secure`, `SameSite=Lax` and `Path=/`.
  - **Links with "verify on new device" off** open without the gate. Their session carries the recipient's first email for the overlay.
  - **Who talks to whom:**
    - The browser only calls the web app's same-origin routes `/api/links/{code}/…`. Those routes refuse a cross-origin `Origin` and non-JSON bodies, which is the CSRF check.
    - The routes forward to the API with the cookie values in `X-Viewer-Device` / `X-Viewer-Session` headers, and set the cookies themselves.
    - The API never reads cookies.
  - **Rate limits:** `/links/*` has its own per-address budget, `RateLimiting__LinkPermitsPerMinute` (30), on top of the per-email limits above.
  - **Logging:** wrong codes, spent codes and refused emails are structured warnings with the link id only, never the email or code.
  - **After the gate:** the real player page is V-2b (SSD-125). Until it lands, `/r/{code}` with a session shows the gate's "You're in" step.
- **Public home page** (`drive.ss-sport.co`):
  - Visitors search players by name, with a position filter.
  - A result shows the full player page (photo, name, position, flag, counts), but **videos, stats and PDFs are blurred and locked**. The backend must not send real media or document URLs for locked pages.
  - **Request access** form: email + description ("club or agency, role, what you're looking for").
  - **Anti-spam:**
    - The email must be OTP-verified before the request is created.
    - Cloudflare Turnstile protects the form.
    - Rate limits apply per IP, per email and per player.
  - The request goes to admins (console + bot).
  - **When an admin approves it, a normal personal `/r/` link is created automatically and emailed to the requester.**

- **Access requests:** a dedicated admin page (also announced by the bot) where admins review each request and approve, approve with changes (expiry, players) or decline. Approval auto-creates the personal link and emails it.

## 7b. Team users, roles & audit log (D-7, owner-approved 2026-10-24)

- **`User` is a team member** (analyst or admin), identified by a unique **Telegram id**. Viewers are not users; they get their own accounts (P-5).
  - **Fields:** Telegram id, username (no `@`), display name (1–100), optional **email**, role, status, when access was requested and when the user was last active.
  - **Status flow:**
    - The bot's request creates a `Pending` analyst.
    - `Approve(role)` → `Active`; `Decline` → `Declined`.
    - `Remove` → `Removed`. The record is kept.
    - A declined or removed user who writes again goes **back to `Pending`** on the same record.
    - Events: `UserRequestedAccess`, `UserApproved`, `UserDeclined`, `UserRemoved`, `UserRoleChanged`.
  - **The first admin** comes from configuration (`Telegram__AdminUserId` plus an email) and is `Active` + `Admin` straight away.
  - **An admin must have an email** for console magic-link sign-in. Approving or promoting to Admin without one fails (`user.admin_needs_email`), and an admin's email cannot be cleared.
  - **Never remove or demote the last active admin.** This needs a count, so the Application layer enforces it (A-8).
  - Notification rules (quiet hours, throttle) are global settings since T-8 (§3a, "Notification rules"); per-user preferences are not planned.
- **Roles** are `Analyst` and `Admin`. The list is closed but extensible: new roles are added in code. Names match the role claims the API checks.
- **`Player.AnalystId`** is the analyst responsible for a player. It is empty for archive players. `AssignAnalyst` sets or reassigns it: removing a user reassigns their players to a chosen admin.
- **`AuditEntry`:**
  - Fields: actor (empty = the system), action code (`user.role_changed`), target type + id, optional JSON-object data (≤ 4000 characters), time.
  - Entries are **append-only**.
  - **Data must not contain email addresses** (`audit.data_contains_email`); people are referred to by id.
  - Writing entries is wired up with each sensitive feature: roles (A-8), links (L-1), hide/delete/restore.
- **`EmailAddress`** is a shared value object: trimmed, lower-case, at most 254 characters. Its `ToString()` is **masked** (`s***@club.com`), so an address dropped into a log is not exposed.

## 8. Email

- **Video player:** **Media Chrome + hls-video-element** (MIT, free, light). hls.js loads only where native HLS is missing; iOS Safari plays natively. Frame stepping (`,` `.`) is custom.
  - **V-3 implementation (2026-10-30):**
    - iPhone/iPad Safari, and any browser without Media Source Extensions, play natively and never download hls.js. Desktop browsers (desktop Safari, and Chrome where it has native HLS too) use hls.js, loaded lazily, because only hls.js exposes the renditions for the quality menu and honours the 360p start (brief §10).
    - Playback starts at the lowest rendition (`startLevel: 0`, i.e. 360p) and adaptive bitrate climbs from there.
    - Speed menu 0.25×–2×; quality menu (Auto + each rendition); frame step by buttons and `,` `.`, pausing first. Frame rate defaults to 30 fps until ingest records each video's real rate.
    - No download anywhere: context menu blocked, no download button, `controlslist="nodownload"`, and picture-in-picture and casting are off (the moving email overlay of V-4 cannot follow the video into those).
    - Controls auto-hide while playing. On phones the mute button and volume slider are hidden (the device's buttons are used) so the controls fit one row of 44 px targets.
    - `/design/player` is a development-only preview using a public Mux HLS test stream; production answers 404.
- **V-2 player page (2026-10-30):**
  - Built from the canvas's Main, Tablet and Mobile artboards. Desktop rules come first; tablet (≤1024 px) and phone (≤640 px) restyle the same markup. Pieces that move between breakpoints (the "Prepared for" ribbon, the personal note) are rendered in each place and shown only where they belong.
  - Data contract `PlayerPageData` (player, recipient, note, stats, videos, documents). Until L-1 serves real personal links, `/design/player-page` shows the canvas's sample player (development only, 404 in production).
  - Missing media fall back to the canvas look: a silhouette until the cut-out photo exists (I-7), tinted gradients until thumbnails exist (I-4), drawn page cards for PDFs until previews exist (I-4).
  - Flags: `country-flag-icons` (MIT), drawn as inline SVG on the server, so no flag code reaches the browser.
  - **V-4 email overlay (2026-10-31), as decided above:** the viewer's email at 20 % opacity, 2.2 % of the frame height (sized from the frame width with container units, so it scales with the player), moving every 8 s with a 0.5 s cross-fade to a random spot that is fully inside the frame and clear of the logo (top-left) and slogan (bottom-right) corners.
    - Fullscreen takes the whole player frame (Media Chrome `fullscreenElement`), so the overlay stays on screen in fullscreen; picture-in-picture and casting are off (V-3).
    - It cannot be clicked or selected, and screen readers skip it. Removing it, hiding it, changing its opacity, class or text in developer tools is undone at once (a MutationObserver guard).
    - The canvas prototype's five fixed overlay positions are dropped in favour of the random spots above.
    - The email comes from the OTP-verified session once L-2 lands; the previews use the canvas's `j.demir@aurora-volley.example`. The visual tests mask the overlay because its position is random.
  - The canvas has no sticky mini-player on phones (the brief mentions one), so none was built; it can be added later if wanted.
  - On phones the short player shows only the big play button before the first play, then the control bar (play, time, speed, quality, fullscreen). That matches the mobile canvas and keeps the two from overlapping.
  - Picking a video from the playlist plays it straight away. Playwright visual tests at 1440 / 834 / 390 px are the "visual pass"; their Linux baselines are generated and checked in the Playwright Docker image, in CI as well.
- Brand tokens, page structure and the motion system are as in brief §10, except for the fonts and contact changes above.
- **The design canvas is matched exactly, down to every detail** (owner, 2026-10-29, for V-1 and every later viewer page). Where the canvas and the brief differ on a value, the canvas wins; the brief still sets behaviour the canvas cannot show (for example counters start when visible).
- **V-1 implementation choices (2026-10-29):**
  - Fonts load through `next/font/google` with Latin + Latin Extended. They are downloaded at build time and served from our own origin, so viewers' browsers never call Google.
  - The logo and infinity mark are the canvas's own PNGs (`web/public/brand/`), so the site looks exactly like the canvas.
  - Tokens, motion and shell styles live in `web/src/styles/`, scoped to `.viewer`, so the Telegram Mini App keeps its own look.
  - **Intro once per page:** the first visit to a page plays the full intro; later visits to that page get the 400 ms fade. The choice is remembered per page in `localStorage` and made by an inline script before the first paint. Blocked storage always gives the full intro.
  - The name's light sweep keeps the canvas values (white 55 %, soft-light, 4.5 s after a 2.4 s delay) but does not repeat its gradient: the canvas's repeating gradient left a still grey box over the name between sweeps.
  - Framer Motion is added only with the pieces that need it (mobile sheet, email gate steps), not in V-1.
  - `/design/shell` is a development-only preview of the shell built from the canvas's sample player; production answers 404.
